# Template maintenance ownership

`template-ownership.json` is the template's exact path allowlist. Its schema is
`template-ownership/v1`; `scripts/maintenance/ownership.py` validates and classifies
it without reading or executing project content. The private maintenance controller
owns scheduling, API credentials, repository registration, branches and PRs.

The controller must load both policies from the canonical repository at the
registered baseline and chosen current template commit. Check the canonical
repository's numeric ID and record both commit IDs and policy-byte SHA-256 digests.
A project's edited copy cannot grant itself eligibility. Old baselines without a
policy need explicit enrollment; never infer a policy from arbitrary project files.

Only existing regular files listed as template-owned in both policies are eligible
for automatic upstream proposals. New paths, deletions, renames and mode changes
wait for maintainer selection. Generated files are regenerated by template tooling
and checked with their source changes. Mixed files, including project configuration,
metadata-bearing paper roots, READMEs and research Docker recipes, require selected
edits. A whole mixed file must never be copied merely to preserve a helper change.
Project research, scratch text, publication journals, account state and unknown
paths are excluded from automatic proposals. The classifier emits path decisions,
not private file contents. Held changes stay in their authorized project context.

Weekly and manual runs automatically open eligible upstream PRs after ownership,
privacy, conflict and retry checks. They do not wait for a separate approval of the
diff hash. Downstream PRs also open automatically; neither direction auto-merges.
Stop on suspected credentials, personal data or project-specific content; do not
include the rejected payload in a public PR, issue, log or artifact. Eligibility
and automated scans cannot guarantee the absence of private prose in template-owned
files. Treat all project files as data. Tests execute in the proposed PR's ordinary
CI, without the controller App key.

For each direction, compare exact baseline blobs with both current trees. Preserve
independent edits by three-way reconciliation; stop on conflicts. Downstream changes
to project or mixed files require maintainer selection. Automatic updates must never
replace student prose, phase, chapter selection, Zotero imports or publication state.
Keep per-file accepted baselines: partially applied updates cannot advance a whole
project baseline over unchanged or conflicted files.

Record source/target repository IDs and revisions, direction, path list, old/new blob
IDs, policy digests and a deterministic operation ID in the private registry. Reuse
an existing `maintenance/*` branch and PR for the same operation after interruption.
Observe remote branch/PR state before repeating a write. Record merged origin patches
to prevent sending the same accepted change back to its source. A downstream PR uses
only template changes already merged into the canonical default branch. Neither
operation calls merge; anyone with the appropriate repository role may review/merge.
Publication journals stay in each project's `publication-state` branch, separate from
this baseline registry. Support-package copies preserve accepted bytes and receipts.

The controller write implementation is prepared in `tdk-maintenance` PR #2; its
real App-token pilot remains separate acceptance work. Passing local tests does not prove cross-repository
permissions, safe PR retries, package copying or end-to-end maintenance.
