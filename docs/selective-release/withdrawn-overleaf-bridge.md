## Paper component and Overleaf boundary

The accepted bridge maps the contents of monorepo `paper/` to the Overleaf project root. Keep paper compilation, bibliography, figures, macros and required template resources self-contained under `paper/`. Build locally/CI from that directory; no monorepo-root TeX proxy is needed for this mapping. Copy generated figures from code/benchmark/proof into declared paper inputs with their provenance, rather than introducing parent-directory imports or symlinks. Shared orchestration can stay at monorepo root, but the exported paper must compile without it.

Manifest source paths remain monorepo-relative; archive paths can strip the `paper/` prefix when producing a standalone paper-source archive. Paper build outputs are explicitly declared generated inputs, not incidental tracked PDFs. The evaluation examples use `benchmark/`, replacing the earlier experiments naming; the coordinator interprets this as a top-level component alongside `code/` and `proof/`. `scratch/`, `proof/`, and `presentation/` are independent components, not automatically published records. Proof sources/results can be selected with the same explicit file rules once their package and citation requirements are chosen. `proof/` must offer optional profiles for Lean, Tamarin, ProVerif, TLA+, and language verifiers for Rust, Java, Go and Solidity; no universal prover or requirement to run every profile is implied. The coordinator-owned `docs/proof-tool-options.md` supplies the verified tool catalog. A selected proof package records the applicable profile, tool version and invocation/evidence needed to reproduce its claims; unselected profiles do not block that release.

`scratch/` is a version-controlled research workspace. Temporary outputs and secrets are ignored, and scratch content is excluded from publication by default. Git tracking is not permission to publish: including any scratch file requires an explicit reviewed package selection. Ignore rules do not remove previously tracked content; package verification must still check the selected bytes.

Bridge execution location, trigger and invocation policy remain undecided. This contract requires no local-only bridge and no manual local command; the common-base, receipt and retry requirements apply to whichever execution model is selected.

There is one Overleaf editor; multi-person collaboration is not an acceptance requirement. Git-side edits and that editor's Overleaf edits can still diverge. The sync workstream owns common-base reconciliation, conflict resolution, operation receipts and retry safety. Release preparation must not perform a last-minute forced export or overwrite either side. For a release intended to include current Overleaf work, first reconcile and commit it, then freeze the resulting monorepo SHA. An explicitly requested historical SHA remains a historical release; do not silently advance it to the latest Overleaf state.

When a release claims synchronized paper state, capture the bridge's verified common-base/content digest and observed Overleaf revision alongside the source SHA; stop if synchronization is unresolved. Do not demand that the remote remain unchanged forever after freezing the snapshot. DOI writeback is a new Git-side paper edit and passes through the same bridge. If the sole editor changes Overleaf meanwhile, merge against the recorded base or stop on conflict; never push the writeback as an unconditional replacement. API success followed by a lost response must be reconciled by the bridge before retry. No second Overleaf editor or collaborator role is introduced by this publication contract.
