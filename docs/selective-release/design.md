## Findings and limits of verification

The documented deposit API creates drafts with POST `/api/deposit/depositions`, updates metadata with PUT, uploads bytes to the returned `links.bucket`, and publishes with a separate POST action. New versions use the latest version's deposition ID, then follow `links.latest_draft`; the action response identifies the old resource. First drafts need `deposit:write`; new-version creation needs `deposit:actions`, which also allows publishing. Reserved DOI metadata does not establish publication. The client must preserve sandbox/production separation and validate returned link origins before forwarding credentials. [Zenodo API](https://developers.zenodo.org/)

## Packaging contract

`manifest.schema.json` describes an explicit input manifest. `example-separate.json` and `example-bundled.json` demonstrate alternatives, not approved paths, licenses or creator identities. Examples are illustrative and must not be uploaded unchanged. First implementation uses exact files, with no implicit directory recursion or globs. A future helper can generate the manifest for review. Record metadata is supplied separately per record and validated against the API; it must not be copied indiscriminately from a repository-wide `.zenodo.json`.

The trusted release tool resolves the requested tag/revision once to a full Git commit ID, fetches that object, and uses that SHA throughout. It records the control-tool commit independently. On a resumed operation, a moved tag is an error. Build selected sources in a clean, isolated checkout with no upload credentials. Package tracked blobs from that commit, never the incidental working tree. Generated outputs come only from declared build profiles and named files. Build profiles are maintained configuration, not executable strings in dispatch inputs.

Reject absolute paths, parent/current-directory segments, backslashes, NULs, symlinks, gitlinks, duplicate output names, duplicate archive members and case-insensitive collisions. Verify all selected tracked blobs exist. Reject untracked or ignored files rather than silently importing them. Use regular files only. Explicitly account for external datasets by immutable identifier, size and digest; unsupported external/LFS/submodule inputs must fail, never archive a pointer as the dataset. The v1 schema now supports explicit `verified_reference` inputs backed by the locally validated acceptance receipt described below.

Create sorted ZIP entries with fixed timestamps, permissions and compression settings. Record SHA-256 for each member and final package. Byte-for-byte packaging of the same staged input must be deterministic; a PDF build may still vary, so do not claim reproducible builds without separate evidence. Inspect generated PDFs and other binaries for unwanted metadata as part of content review. Every package includes selected licensing and reproduction instructions. Validate that declared licenses cover included third-party material.

Dockerfiles, `.dockerignore` and container build configuration are source eligible for explicit reproduction-package selection. Actual images are separate optional built outputs: record image digest and platform, and select an OCI archive explicitly if bytes are to be included. Immutable GitHub releases do not freeze mutable GHCR tags.

Each archive contains a non-circular `PROVENANCE.json` with source SHA, manifest digest, tool SHA, build profile and dependency/container digests, and member hashes. The filename is reserved. Package hashes go in an external release receipt; the archive cannot contain its own final hash. Runtime logs, credentials, `.git`, scratch material, review comments, local paths and unpublished content are not implicitly included. Source-repository URLs and user identities in provenance are explicit disclosure choices.

```

release-tool build --plan PLAN --out BUNDLE
```

## State, reconciliation and retries

Proposed durable registry key: `(repository immutable ID, target environment, logical record key)`. Proposed operation key adds source SHA, manifest digest, metadata digest and package-set digest. Keep sandbox and production IDs/tokens/state separate. Durable operation storage uses compare-and-swap and a persistent writer lock; the accepted maintenance controller owns registry access. Existing-branch GitHub Contents and durable POSIX file adapters are implemented; the actual authorized controller connection must be supplied before live CI use. Registry permissions and auditability support lead-student ownership, advisor review and recovery without pretending student workflow write access creates an independent approval boundary. Per-run temporary files and expiring artifacts alone are insufficient. Do not use secrets or access tokens as identifiers.

Each record tracks the current deposition ID, prior/latest published deposition ID, concept DOI when available, reserved/version DOI, source SHA, package inventory/hashes, operation ID, and state:

```
planned -> creating -> draft -> uploading -> staged -> publishing -> published -> writeback_done
                 \-> outcome_unknown (reconcile before another write)
```

Commit intent before create/newversion; persist the returned ID immediately. Record timestamps and sanitized response identity, not authorization headers. A crash can happen between the remote write and local persistence: the API documentation offers no idempotency key that closes this gap. Do not promise exactly-once creation. Recover by paginated authenticated deposit listing and comparison with the saved intent and an operation marker included in the supported description metadata. If the marker was not yet applied, or zero/multiple candidates remain after bounded reconciliation, stop for explicit recovery. Never invent a match from title alone or automatically create another draft. New-version operations first inspect the existing latest draft and verify its ownership/operation association.

For GET, use bounded exponential backoff with jitter for temporary network failures, 429 and retryable 5xx, honoring Retry-After. Authentication, permission and metadata-validation failures require correction. For any potentially committed write (including timeouts/5xx), read current state before retry. An ambiguous create/newversion/publish cannot be blindly replayed. Upload retries compare filename, length and server-reported checksum; use documented checksum algorithm and independently retain SHA-256. Re-open the stream at offset zero for a full retry. Unexpected files or changed same-name content in a draft stop reconciliation rather than deleting someone else's edits. Explicit replace/remove operations require a new reviewed plan.

New-version staging records the previous published inventory and removes only unchanged inherited files that differ from the reviewed new bundle; unexpected edits stop. Published records are not rewritten to match a rerun. A matching published receipt is success; different bytes require a new version. In multi-record releases, record A can publish while B fails. There is no cross-record transaction: report partial publication, preserve A, and resume B. Do not retract A or manufacture a replacement DOI. A 202 publish response is not sufficient evidence; poll boundedly for published state, then verify files and identifiers and distinguish DOI-resolution delay from a failed publish.
