\section{GitHub}\label{app:code:github}
Keep your work in the three GitHub repositories described in \cref{app:start:access}: code, models, notes, drawings, PDFs, slides and the Overleaf-synced paper. Readers can access code anonymously for double-blind review through \href{https://anonymous.4open.science/}{Anonymous GitHub}, or as a permanent DOI archive through Zenodo (\cref{app:zenodo}).

\paragraph{Repository layout.} The notes repository's submodules (\cref{app:start:access}) keep the histories separate within one clone:
\begin{itemize}[noitemsep]
  \item notes repository: \texttt{README.md} linking the pieces; \texttt{notes/} for notes and drawings, with consultation summaries in \texttt{notes/consultations/}; \texttt{slides/} for consultation slides and the presentation;
  \begin{itemize}[noitemsep]
    \item \texttt{paper/}: submodule, the Overleaf-synced paper repository, with the TikZ sources of every figure in \texttt{figures/};
    \item \texttt{code/}: submodule, the code repository: the code in \texttt{src/} and \texttt{tests/}, the measurement scripts and their raw results in \texttt{experiments/}, and at the root \texttt{README.md}, \texttt{LICENSE}, \texttt{.zenodo.json}, \texttt{CITATION.cff}, the \texttt{justfile}, the \texttt{Dockerfile} and \texttt{.devcontainer/}.
  \end{itemize}
\end{itemize}
For a larger effort, add separate \texttt{proof/} and \texttt{demo/} repositories as pinned submodules when they have distinct owners or toolchains. Keep \texttt{paper/} as the LaTeX repository; do not rename existing student checkouts to adopt a diagram's naming. Each artifact needs its own documented build, appropriate checks and CI. The notes repository remains the common map of decisions and compatible revisions. A small project can keep proofs and demos in \texttt{code/}.

Include the code and data behind the paper's results in each release (\cref{app:zenodo}).

\paragraph{One command.} The \href{https://github.com/BlackLight54/tdk-code-template}{tdk-code-template} provides the layout above, Zenodo files, Docker images and one GitHub Actions workflow per recipe: \texttt{ci} (build, test and smoke reproduction), \texttt{evaluate}, \texttt{benchmark}, \texttt{robustness}, \texttt{demo} and \texttt{release}.

Put recurring commands in a \texttt{justfile} for the \href{https://github.com/casey/just}{just} command runner. We require that \texttt{just reproduce} regenerates every paper figure and table. Name individual recipes after their outputs: \texttt{just fig-scalability} for the scalability figure (\cref{fig:guide:scalability}) and \texttt{just tab-robustness} for the robustness table (\cref{tab:guide:robustness}). Provide \texttt{just reproduce --smoke} with a reduced workload that finishes in minutes. GitHub Actions runs it on every push to catch broken README commands.

\section{The checks and paper CI}\label{app:code:paperci}
The paper repository's \texttt{.github/workflows/paper.yml} builds both PDFs on pushes to \texttt{main} or \texttt{master}, non-draft pull requests and manual runs. It runs each rule in \texttt{scripts/lint.lua} as a separate step. The run page shows each result and annotates findings at the relevant file and line. Each annotation names the problem and the remedy, including replacement text where the lint can supply it. The job summary starts with the essentials (\cref{app:writing:essentials}): a line of marks, then a row per essential. A second table groups the other rules as on the Checks page. There are three rule families; \texttt{texlua scripts/lint.lua list} describes each rule, with its severity and phase.
\begin{description}[noitemsep]
  \item[source] Checks the sources and build log. Gates cover phase-appropriate essentials (\texttt{essentials}), the template structure (\texttt{frame}) and a clean build (\texttt{build}, \texttt{overfull}); the chapter-order check (\texttt{spine}) only advises. They also check floats, captions, axes, tables, labels, references, acronyms, listings, the shape of the reference list, typography, consistent terms, that no TDK paper of the same year is cited or linked (\cref{app:tdk:companion}), headline numbers against the evaluation, and completion of the AI declaration and title page. The burn-down rules for placeholders and beats only report, and the \texttt{burndown} rule writes their counts as one line of JSON for CI to collect over time. A rule that cannot run, because a tool is missing or the profile excludes it, says \emph{skipped}, never \emph{pass}.
  \item[pdf] Checks the reviewer PDF against the form requirements (\cref{app:tdk:form}), even if you replaced the template. Checks cover the paper size, metadata, embedded fonts, a 15\,MB limit and the body font: \texttt{pdf-font} fails on a font that is not a serif or not 12\,pt, and only warns on a serif other than Times. The 15\,MB limit is our safeguard, taken from the faculty's thesis guideline (\texttt{include/guideline.tex}); it is not a TDK rule. They measure line spacing from line pitch and margins from the text on every page. They report text below 8\,pt, count main-text pages from the PDF outline, and check required parts, including both abstracts and the AI declaration. For a thesis, \texttt{LINT\_PROFILE=thesis} applies the faculty's thesis thresholds.
  \item[tools] Reports from TeX Live and container tools: chktex and lacheck for typography, texcount for chapter word counts and abstract length, checkcites for uncited reading-list entries, the BibTeX log, aspell on the detexed chapters for unknown words and mixed British and American spellings, and a link check. These report and never block the build, with one exception: \texttt{repo-hygiene} fails at every phase when the repository tracks build output such as a PDF, a log or an \texttt{.aux} file.
\end{description}
Each rule has a \emph{severity} and a \emph{phase}. A \emph{check} fails the run, \emph{advice} warns, and a \emph{count} reports numbers. A check whose phase is \texttt{always} fails at every phase: \texttt{essentials}, \texttt{frame}, \texttt{chapters}, \texttt{build}, \texttt{overfull}, \texttt{figures}, \texttt{labels}, \texttt{crefs}, \texttt{bib}, \texttt{companion}, \texttt{code}, \texttt{preamble} and \texttt{repo-hygiene}. The other checks become required at \texttt{draft}, \texttt{polish} or \texttt{submit}; before then, they only report. The phases are those of the lifecycle (\cref{app:lifecycle}): \texttt{topic}, \texttt{setup}, \texttt{research}, \texttt{plan}, \texttt{draft}, \texttt{polish} or \texttt{submit}. The first four share the checks' first level, and the lint rejects any other value. Page count blocks only on \texttt{main} or \texttt{master}, so a branch may be short while you draft a chapter. Locally, \texttt{make check} runs every rule against the draft build, \texttt{make check-reviewer} against the reviewer PDF, and \texttt{make check-submit} against the reviewer PDF at the \texttt{submit} phase whatever \texttt{\textbackslash lintphase} says, the check before you upload; run one rule with, for example, \texttt{make lint-essentials}. The same lint generates the draft PDF's \emph{Checks} page on every compile (\cref{app:latex:todo}), keeping the PDF and CI consistent.

The workflow is part of the Overleaf template and is copied into each new student project. Overleaf's GitHub sync creates the student's repository; its first push starts CI. View runs under GitHub's \emph{Actions} tab or on a pull request.
\paragraph{Lifecycle CI.} The notes repository from \href{https://github.com/BlackLight54/tdk-notes-template}{tdk-notes-template} has a separate workflow. Every push and Monday morning, it regenerates \texttt{lifecycle.md} with file-based checks. It checks that the three anchors in \texttt{notes/anchors/} are longer than stubs, counts summaries in \texttt{notes/consultations/}, and checks that submodules have moved within two weeks. It also checks for the code README, license, justfile, tests, Dockerfile and Zenodo file, and requires slides before the conference. Due phases come from the paper's \texttt{\textbackslash lintphase}.

Paper CI uploads the paper's burn-down counts as \texttt{burndown.json} with every run; the notes repository's lifecycle workflow appends them to \texttt{burndown.csv}, plots \texttt{burndown.svg} and commits both for consultation use. These checks inventory the work; we still assess its quality.

\section{Running the reviewer passes}\label{app:code:reviewers}
\paragraph{Self-score and reviewer passes.} The paper repository carries two agent skills in \path{.claude/skills/}, so each commit has the skills that review it. On main-branch pushes, non-draft pull requests and manual runs, paper CI uploads the evidence of that commit as one artifact: both PDFs, the build logs, the lint output and the skim view, kept for 14 days. \path{.claude/skills/self-score/} scores the artifact's \texttt{reviewer.pdf} A--E using the review sheet's wording and page references, and identifies the weakest criterion and cheapest fix. \path{.claude/skills/reviewer-passes/} runs the skim reviewer and expert panel on the same artifact. \texttt{scripts/review/review.py} fetches the artifact of a named commit and checks its hashes. Self-score writes nothing; the reviewer passes write nothing unless you record a run. \Cref{app:lifecycle:reviewers} says what the passes are and when to run them; this section says how.

\paragraph{Running them.} Push your commit and run paper CI, through a non-draft pull request or a manual workflow dispatch (\cref{app:code:paperci}). Then, in your paper repository, ask your agent to run the reviewer passes, or name one persona: \enquote{review as the cryptographer}. The skill in \path{.claude/skills/reviewer-passes/} fetches the CI artifact of that commit with \texttt{scripts/review/review.py}, which refuses an artifact whose hashes do not match. It gives each persona a directory holding only that persona's inputs: the reviewer PDF, the skim view, or both, and your spine if you name the file. Without a spine, a persona judges overclaiming against the abstract and the introduction. Each persona runs apart from the others and never sees another persona's findings or an earlier run. The chat response gives each persona's worst finding, the criterion and page, and the cheapest fix. It then lists the three cheapest changes overall. Ask a persona for more to see its remaining findings.

\paragraph{Recording a run.} By default the skill writes no files and never edits the paper. You choose the fixes, and the consultation summary (\cref{app:consult}) records your decisions. We record a run at three milestones (the spine premortem, the full draft and before upload), and you may record any run you choose. A recorded run becomes one issue on your paper repository: the panel, the skim scores, one checkbox per finding, and the hashes of the artifact and of each persona's inputs. Propose a disposition for each finding in a comment on the issue: \texttt{F3 fixed in <sha>}, \texttt{F4 rejected: <reason>} or \texttt{F5 deferred}. We confirm the dispositions with the label \texttt{review-confirmed}. The issue is not an input to the next run, and the skill keeps no memory between runs. Rerun it on the revised paper to check whether the fixes answer the objections.

Ignore findings that do not identify a place in the paper. Verify every suggested source before citing it; a persona may invent one. Tell us if two personas raise the same concern or one argues outside its remit, so we can fix their boundaries in the persona files.

\section{The README}\label{app:code:readme}
Every TDK needs a \emph{results} repository that lets reviewers reproduce its numbers. Some also produce a reusable \emph{tool}. The code template's \texttt{README.md} starts with the results sections. Extra tool sections appear in a commented block below: delete the block for results only, or uncomment it for a tool.

\paragraph{The results README.} In this order:
\begin{enumerate}[noitemsep]
  \item What this is, in two sentences, with the paper's title and the concept DOI badge (\cref{app:zenodo}).
  \item The reproduction command: \texttt{docker run \dots{} reproduce} for every figure and table (\cref{app:code:docker}). Follow it with \texttt{just reproduce} for local clones and a list of pinned dependencies. Keep dependencies to a minimum.
  \item A results map with one row per paper figure and table: its number, reproduction command, output path and wall-clock time on specified hardware.
  \item Reproduction limits: secrets, special hardware, long runs or nondeterminism, including the seed policy and expected variance. Keep this section even if everything reproduces with fixed seeds.
  \item The results tag: which Git tag and Zenodo version the paper's numbers came from (\cref{app:zenodo:versions}).
  \item How to cite, and the license.
\end{enumerate}

\paragraph{The tool README} adds installation, use on the reader's own input with a worked example, contribution instructions and maintainers after the results sections. Follow the conventions of the open-source foundations we work with, such as \href{https://github.com/LF-Decentralized-Trust/lab-proposals/blob/main/README.md}{LF Decentralized Trust Labs}: an Apache 2.0 \texttt{LICENSE}, a \href{https://developercertificate.org/}{Developer Certificate of Origin} sign-off on every commit (\texttt{git commit -s}), \texttt{MAINTAINERS.md} and a \texttt{SECURITY.md} with vulnerability-reporting instructions. A compliant tool can be proposed as a lab after the TDK.

\section{Docker}\label{app:code:docker}
Make \texttt{docker run} the simplest way to reproduce results. We assume a computer science reviewer has Docker; see Docker's \href{https://docs.docker.com/get-started/}{Get started} if you are new to it. The code template provides two images:
\begin{itemize}[noitemsep]
  \item The \textbf{runtime image} is built by the root \texttt{Dockerfile}, with \texttt{just} as its entry point. Run \texttt{docker run --rm -v \$PWD/out:/out ghcr.io/<you>/<repo> reproduce} to regenerate all results into \texttt{out/}, or \texttt{\dots{} fig-scalability} for one figure. Pin every dependency to make the environment independent of the reviewer's machine.
  \item The \textbf{development image} includes the toolchain, language servers and test runner. Its \texttt{.devcontainer/devcontainer.json} follows the open \href{https://containers.dev/}{Development Containers} specification. VS Code, GitHub Codespaces and Docker's development environment feature can open the repository ready for work. We use the same environment when helping you.
\end{itemize}
A \href{https://docs.github.com/en/actions}{GitHub Actions} workflow builds both images on every push and publishes the runtime image to the \href{https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry}{GitHub Container Registry} on each release. Use the same tag for the image and Zenodo version. We require the README's first command to select the results-tag image.

\section{Demos}\label{app:code:demo}
Record demonstrations with a script in the code repository, never by hand. A script lets you update the recording after code changes and rerun it before the presentation. Have CI publish a fresh recording on every push for the README, the presentation and reviewers.
\begin{itemize}[noitemsep]
  \item For a web UI, we recommend \href{https://playwright.dev/}{Playwright}: it drives the real workflow and saves a video and trace. Draw captions into the frames at each step.
  \item For a backend, CLI or prover such as Tamarin, Lean or a model checker, we recommend recording a scripted terminal session with \href{https://asciinema.org/}{asciinema}. Render it to SVG or GIF, or embed the cast beside the verdicts in HTML. We use this for our backends and proof assistants.
\end{itemize}
Use captions to explain the invariant, rejected attack or result in the running example's terms. Do more than narrate clicks. The code template includes a recorder in \texttt{demo/} and a \texttt{demo} workflow that uploads its recording as an artifact. Run it locally with \texttt{just demo}.

\section{AI tools}\label{app:code:ai}
\paragraph{Tools, as of October 2026.} These recommendations can become outdated within months.
\begin{itemize}
  \item For research, we recommend the strongest models. We prefer Claude Fable and ChatGPT Astra; ask whether we can help with a subscription.
  \item Prefer an agent working in your repository: Claude Code or Codex, ideally through T3 Code, GitKraken Kepler or herdr. This gives the agent access to your files and its repository tools. You \emph{need} version control when AI edits files.
  \item Plugins and skills: the Matt Pocock and poetato plugins for productivity; caveman, ponytail, squeez and TRON if you want to spare tokens. Three we use daily: \href{https://www.aihero.dev/skills-grill-me}{grill-me} (\href{https://claudemarketplaces.com/skills/mattpocock/skills/grill-me}{marketplace page}) interrogates a plan before you build it; \href{https://github.com/cursor/plugins/blob/main/pstack/skills/unslop/SKILL.md}{unslop} takes the machine out of generated prose; \href{https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md}{ponytail} cuts the tokens an agent spends.
  \item We recommend concise instructions. Overloaded \texttt{AGENTS.md} files and memories can impair model performance. Prefer skills that clearly describe the range of tasks they apply to.
\end{itemize}

\subsection{Give routine checks to lint}\label{app:code:agents}
If a lint rule can check an obligation, the agent need not reconsider it on every pass. Run the mechanical checks in \cref{app:code:paperci} and give the agent their findings. Spend its reasoning on the research question, assumptions, evidence and design. The agent still has to understand and fix failures; a green build does not establish that the research is sound.

When a review repeatedly finds the same mechanically decidable mistake, propose a narrow lint rule to the template maintainers, with an example it must reject and a valid example it must accept. Preserve the rule's phase and severity. Questions such as whether an experiment supports a claim belong in review, even when a script can collect the evidence for them.

\subsection{Organise the work around decisions}\label{app:code:orchestration}
Start with one interactive thread for the person responsible for the work. It keeps the decisions, accepts corrections and commissions bounded tasks. Give a subagent the task, relevant files and revisions, acceptance checks and expected output; ask it to return evidence, then stop. Reuse the task recipe on the next run with fresh context. This is how we use subagents as stateless workers, although a runtime may support follow-up messages. Fresh context removes unrelated history; it still needs a sufficient brief.

\paragraph{Agree the scope first.} Use \emph{grill-me} to expose a plan's decision tree. Ask the questions whose prerequisites are settled, investigate facts in fresh workers, and let the owner make the decisions. Turn the agreed answers into worker briefs and acceptance checks. A finding that invalidates an assumption reopens that decision in the interactive thread.

\paragraph{Scale the ownership, then the agents.} For several workstreams, a project leader's thread can coordinate paper, implementation and verification leaders. Each leader can create a persistent worker or subleader thread for a responsible colleague and share its promptable link. The colleague can steer that thread, which runs its own task-scoped workers. The project leader uses the top-level view; workstream leaders may be shared; project members use their subleader threads. Verify actual access permissions when sharing. A small project may need only one leader and a few workers.

Leaders contact one another when a finding crosses a boundary. Name the affected revision, evidence, owner and requested action. For example, if a model checker exposes an assumption missing from the implementation, the code owner investigates a regression case and the paper owner checks the claim. Resolve the finding against compatible paper, code and model revisions. Limit each delegation's scope and further delegation so the same problem does not spawn duplicate work.

\paragraph{Independent checks.} Choose the relevant passes below; running every pass for every edit wastes attention. The existing reviewer and self-score skills are described in \cref{app:code:reviewers}; the other lenses are workflow recommendations, not additional installed checks.
\begin{description}[noitemsep]
  \item[Paper:] substantive review, template guardrails, code--claim alignment and the academic self-score.
  \item[Reuse:] extract common elements, propose new lint rules and consolidate duplicate or conflicting findings.
  \item[Artifacts:] formal proof obligations, code, tests and CI/CD, including reproducible demonstrations.
  \item[AI-style concerns:] inspect specific prose and its sources. An AI detector's output is advisory and cannot establish authorship; record actual AI use as in \cref{app:writing:ai}.
\end{description}
Pin inputs to a revision and keep initial reviews independent of one another's conclusions. Different models and harnesses can expose different objections; the leader resolves them against evidence, not by majority vote. A model checker result must name its scope and assumptions, and a proof claim must have the appropriate checker evidence. A self-score is feedback, not an official grade. Work happens in bounded workers; the interactive thread reviews evidence and decides what happens next. A new independent review also starts with fresh context.

\paragraph{Summaries with evidence.} Each leader returns a short findings record: finding ID, owner, artifact revision, check or run, evidence link, severity, observation time, disposition and next action. The top-level leader can turn those records into an HTML dashboard. Link each status to its evidence and show unchecked, blocked and stale results explicitly. Record accepted decisions in the notes repository; the dashboard is a view of those records. For recorded paper-review runs, retain the issue and confirmation process in \cref{app:code:reviewers}.

\paragraph{Small local instructions.} Keep \texttt{AGENTS.md} short. At directory boundaries that need distinct instructions, state the local purpose, owner, commands and invariants, and link the shared guidance. Do not copy the root policy everywhere. Use \emph{unslop} for readable prose, \emph{caveman} for terse agent exchanges and \emph{ponytail} for the smallest complete change. Preserve constraints and evidence identifiers. \href{https://github.com/tron-format/tron-javascript}{TRON} is a compact structured-data format; validate round trips and measure savings on your records before adopting it.

\paragraph{Small semantic decisions.} An optional System One adapter can answer bounded routing questions, such as which owner should receive a finding. Supply explicit state and typed choices or a scoring rubric; the calling thread retains workflow control. Batch independent questions, resolve dependent ones later, and distinguish unavailable or failed judgments from negative answers. Escalate uncertainty under an evaluated policy. This is separate from deterministic lint and substantive review, and is not required by this template.

\subsection{T3 Code in practice}\label{app:code:t3}
The following is optional tooling guidance, checked in November 2026. T3 Code is a shared frontend for agent harnesses such as Codex and Claude Code. Configure the harness on the machine that runs the work. Its \href{https://github.com/pingdotgg/t3code}{documentation} is the reference for current capabilities; Theo's \href{https://www.youtube.com/watch?v=uLGxb4F3SyI}{T3 Code walkthrough} demonstrates the moves below. We use the documented commands rather than relying on a video's platform-specific shortcuts.

\paragraph{Keep the work on an always-on host.} A home machine or cloud VM holds the repositories, harness login and build tools; the laptop or phone controls it. On a prepared host, run \texttt{t3 connect} (\texttt{t3 up --connect}), approve the sign-in link, then sign into the same account on the client and select that environment. T3 Connect provides connectivity without router forwarding; it does not supply the compute. See the \href{https://github.com/pingdotgg/t3code/blob/main/docs/user/remote-access.md}{remote-access guide}.

Closing the client laptop leaves remotely hosted work running while the host stays awake and its server runs. Linux service setup supports running after logout; check \texttt{t3 service status}. A macOS host must remain logged in and awake. Windows needs the desktop app or terminal server kept running. The \href{https://github.com/pingdotgg/t3code/blob/main/docs/user/background-service.md}{service guide} explains the differences. Try a harmless long check and inspect it from a second client after closing the laptop. Tasks can still pause for input, failures or usage limits.

\paragraph{Switch accounts; keep the thread.} Add accounts in provider settings, then choose a compatible account in the thread's model picker. This avoids manually copying the conversation just to use another account's available capacity. Compatibility matters: \href{https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-codex.md}{Codex} supports shared sessions with separate account credentials; isolated homes do not share sessions. \href{https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-claude.md}{Claude} instances with separate configuration directories keep separate histories. Follow the provider's setup instructions. Account continuation and cross-harness handover preserve context; neither is a fresh independent review, and normal context limits still apply.

\paragraph{Choose a move for the job.} The timestamps below point into Theo's walkthrough; exact controls depend on the installed release. The \href{https://github.com/pingdotgg/t3code/blob/main/docs/user/keybindings.md}{keybinding settings} describe the current shortcuts.
\begin{description}[noitemsep]
  \item[Direct the work:] delegate across models and harnesses (06:37); link another thread (07:56) or drag its reference into the composer (28:43). Steer to correct the current task; queue the next task (18:05). Select text or a preview region to give precise feedback (28:53).
  \item[Manage attention:] send an independent task in the background (19:33), pin an important leader (19:12), stash and restore a draft in the right thread (25:34), and settle or snooze threads (16:20). Inspect usage before increasing the worker count (23:10).
  \item[Inspect and deliver:] render an HTML view (22:41), attach reusable files (34:38), or open the remote checkout in an editor over SSH (32:33). Isolate concurrent edits in worktrees (29:49). Link each pull request to its thread and use PR monitoring (30:34) so check results return without an agent polling loop.
  \item[Trigger bounded work:] schedule a recurring check (17:46), deliver an event through a webhook (31:18), or connect an outside agent through MCP (26:54). Define the inputs and output, avoid duplicate triggers, and grant only the access the workflow needs. These actions require explicit setup; documenting them does not enable them.
  \item[Change perspective or diagnose:] hand an interactive thread to another harness (27:25); use a fresh worker when independence matters. For a T3 problem, \texttt{npx t3 triage} prepares a diagnostic session (33:43).
\end{description}
Use GitHub issues, pull requests and CI to keep accepted changes reviewable. Commit in each artifact repository, then update the notes repository's submodule pointers. Pull the paper changes from GitHub in Overleaf before resuming edits there. A thread's completion is not itself permission to merge or publish.
