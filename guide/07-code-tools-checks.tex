\section{GitHub}\label{app:code:github}
Keep your work in the three GitHub repositories described in \cref{app:start:access}: code, models, notes, drawings, PDFs, slides and the Overleaf-synced paper. Readers can access code anonymously for double-blind review through \href{https://anonymous.4open.science/}{Anonymous GitHub}, or as a permanent DOI archive through Zenodo (\cref{app:zenodo}).

\paragraph{Repository layout.} The notes repository's submodules (\cref{app:start:access}) keep the histories separate within one clone:
\begin{itemize}[noitemsep]
  \item notes repository: \texttt{README.md} linking the pieces; \texttt{notes/} for notes and drawings, with consultation summaries in \texttt{notes/consultations/}; \texttt{slides/} for consultation slides and the presentation;
  \begin{itemize}[noitemsep]
    \item \texttt{paper/}: submodule, the Overleaf-synced paper repository, with the TikZ sources of every figure in \texttt{figures/};
    \item \texttt{code/}: submodule, the code repository: the code in \texttt{src/} and \texttt{tests/}, the measurement scripts and their raw results in \texttt{experiments/}, and at the root \texttt{README.md}, \texttt{LICENSE}, \texttt{.zenodo.json}, \texttt{CITATION.cff}, the \texttt{justfile}, the \texttt{Dockerfile} and \texttt{.devcontainer/}.
  \end{itemize}
\end{itemize}
Include the code and data behind the paper's results in each release (\cref{app:zenodo}).

\paragraph{One command.} The \href{https://github.com/BlackLight54/tdk-code-template}{tdk-code-template} provides the layout above, Zenodo files, Docker images and one GitHub Actions workflow per recipe: \texttt{ci} (build, test and smoke reproduction), \texttt{evaluate}, \texttt{benchmark}, \texttt{robustness}, \texttt{demo} and \texttt{release}, plus \texttt{hygiene}, which checks what must not reach a public repository (\cref{app:zenodo:public}).

Put recurring commands in a \texttt{justfile} for the \href{https://github.com/casey/just}{just} command runner. We require that \texttt{just reproduce} regenerates every paper figure and table. Name individual recipes after their outputs: \texttt{just fig-scalability} for the scalability figure (\cref{fig:guide:scalability}) and \texttt{just tab-robustness} for the robustness table (\cref{tab:guide:robustness}). Provide \texttt{just reproduce --smoke} with a reduced workload that finishes in minutes. GitHub Actions runs it on every push to catch broken README commands.

\section{The builds and what reads them}\label{app:code:builds}
The template has one set of sources and two \LaTeX{} roots, so it builds two PDFs (\cref{tab:code:builds}). You edit \texttt{draft.tex}, which holds the title, \texttt{\textbackslash lintphase} and the chapter list. \texttt{final.tex} is four lines: it sets the \texttt{final} class option, disables todonotes, defines \texttt{\textbackslash finalmode} and inputs \texttt{draft.tex}. Never edit it. Your text lives in \texttt{content/}, and both PDFs print the same paper from it. The names follow \LaTeX{}'s \texttt{draft} and \texttt{final} options, but only the final build sets its option: the class option \texttt{draft} would replace your figures with empty boxes, so \texttt{draft.tex} leaves it out.
\begin{table}[!ht]
  \centering
  \small
  \caption{The two builds.}
  \label{tab:code:builds}
  \begin{tabularx}{\linewidth}{>{\raggedright\arraybackslash}p{0.17\linewidth} >{\raggedright\arraybackslash}X >{\raggedright\arraybackslash}X}
    \toprule
     & \textbf{Draft} & \textbf{Final} \\
    \midrule
    Root & \texttt{draft.tex} & \texttt{final.tex} \\
    Locally & \texttt{make draft} or \texttt{make all} & \texttt{make final} \\

\paragraph{\emph{Final} names the format, not the state of the paper.} A final PDF builds from your first day. It hides every todo, beat and gap marker, so it can look finished while half the paper is missing. Read it every week to see what reviewers will see, and run \texttt{make check-submit} to learn whether it is ready. The draft build is also separate from the \texttt{draft} phase of the lifecycle and from the full draft, the anchor we approve (\cref{app:lifecycle}). You build both PDFs in every phase.

\paragraph{What is made from the builds.} The lint and paper CI produce four more outputs:
\begin{description}[noitemsep]
  \item[Checks page] Part of the draft. On every compile, the lint runs on the sources and prints its findings at the front of \texttt{draft.pdf} (\cref{app:latex:todo}). It runs no PDF rules and does not read the build log, so a clean Checks page does not promise a green CI.
  \item[Skim view] Made by paper CI from \texttt{final.pdf} (\cref{app:lifecycle:reviewers}). It keeps headings, labelled items, boxes and captions, and replaces paragraphs with their length.
  \item[Review bundle] The artifact \texttt{review-<sha7>} that paper CI uploads for one commit and keeps for 14 days: both PDFs, their logs, the lint's output, the skim view and a manifest (\cref{app:code:reviewers}). The self-score and the reviewer passes read this bundle, never a PDF on your machine, so what they judge is tied to a commit.
  \item[Burn-down counts] A separate artifact of paper CI, \texttt{burndown.json}, which the notes repository plots (\cref{app:code:paperci}).
\end{description}

\paragraph{Which check reads which build.} Most rules read only the sources and give the same result for either build. The option \texttt{--doc} picks the build whose log, \texttt{.aux} file and PDF the remaining rules read: \texttt{build}, \texttt{overfull}, \texttt{pages}, \texttt{sources}, \texttt{checkcites}, \texttt{bibtex-log} and every \texttt{pdf-} rule. Read those results on the final build, because the draft's notes and guide change its page count, its margins and its text.
\begin{description}[noitemsep]
  \item[\texttt{make check}] The draft build, at your \texttt{\textbackslash lintphase}. Its PDF rules also measure the notes and this guide, so prefer the next command.
  \item[\texttt{make check-final}] The final build, at your \texttt{\textbackslash lintphase}. Paper CI runs the same rules on the same build.
  \item[\texttt{make check-submit}] The final build, at the \texttt{submit} phase whatever \texttt{\textbackslash lintphase} says. This is the check before you upload.
\end{description}
No reviewer persona reads \texttt{draft.pdf}. The skim reviewer reads the skim view, and the expert personas and the self-score read \texttt{final.pdf}.

\section{The checks and paper CI}\label{app:code:paperci}
The paper repository's \texttt{.github/workflows/paper.yml} builds both PDFs on pushes to \texttt{main} or \texttt{master}, non-draft pull requests and manual runs. It runs each rule in \texttt{scripts/lint.lua} as a separate step. The run page shows each result and annotates findings at the relevant file and line. Each annotation names the problem and the remedy, including replacement text where the lint can supply it. The job summary starts with the essentials (\cref{app:writing:essentials}): a line of marks, then a row per essential. A second table groups the other rules as on the Checks page. There are three rule families; \texttt{texlua scripts/lint.lua list} describes each rule, with its severity and phase.
\begin{description}[noitemsep]
  \item[source] Checks the sources and build log. Gates cover phase-appropriate essentials (\texttt{essentials}), the template structure (\texttt{frame}) and a clean build (\texttt{build}, \texttt{overfull}); the chapter-order check (\texttt{spine}) only advises. They also check floats, captions, axes, tables, labels, references, acronyms, listings, the shape of the reference list, typography, consistent terms, that no TDK paper of the same year is cited or linked (\cref{app:tdk:companion}), headline numbers against the evaluation, and completion of the AI declaration and title page. The burn-down rules for placeholders and beats only report, and the \texttt{burndown} rule writes their counts as one line of JSON for CI to collect over time. A rule that cannot run, because a tool is missing or the profile excludes it, says \emph{skipped}, never \emph{pass}.
  \item[pdf] Checks the final PDF against the form requirements (\cref{app:tdk:form}), even if you replaced the template. Checks cover the paper size, metadata, embedded fonts, a 15\,MB limit and the body font: \texttt{pdf-font} fails on a font that is not a serif or not 12\,pt, and only warns on a serif other than Times. The 15\,MB limit is our safeguard, taken from the faculty's thesis guideline (\texttt{include/guideline.tex}); it is not a TDK rule. They measure line spacing from line pitch and margins from the text on every page. They report text below 8\,pt, count main-text pages from the PDF outline, and check required parts, including both abstracts and the AI declaration. For a thesis, \texttt{LINT\_PROFILE=thesis} applies the faculty's thesis thresholds.
  \item[tools] Reports from TeX Live and container tools: chktex and lacheck for typography, texcount for chapter word counts and abstract length, checkcites for uncited reading-list entries, the BibTeX log, aspell on the detexed chapters for unknown words and mixed British and American spellings, and a link check. These report and never block the build, with one exception: \texttt{repo-hygiene} fails at every phase when the repository tracks build output such as a PDF, a log or an \texttt{.aux} file.
\end{description}
Each rule has a \emph{severity} and a \emph{phase}. A \emph{check} fails the run, \emph{advice} warns, and a \emph{count} reports numbers. A check whose phase is \texttt{always} fails at every phase: \texttt{essentials}, \texttt{frame}, \texttt{chapters}, \texttt{build}, \texttt{overfull}, \texttt{figures}, \texttt{labels}, \texttt{crefs}, \texttt{bib}, \texttt{companion}, \texttt{code}, \texttt{preamble} and \texttt{repo-hygiene}. The other checks become required at \texttt{draft}, \texttt{polish} or \texttt{submit}; before then, they only report. The phases are those of the lifecycle (\cref{app:lifecycle}): \texttt{topic}, \texttt{setup}, \texttt{research}, \texttt{plan}, \texttt{draft}, \texttt{polish} or \texttt{submit}. The first four share the checks' first level, and the lint rejects any other value. In CI, raw lint exit 1 is an advisory paper finding; raw exits above 1, compilation failures and other technical errors fail the workflow. The template repository also runs regression and consistency checks; student copies do not run template-skeleton checks. Locally, \texttt{make check} runs every rule against the draft build, \texttt{make check-final} against the final PDF, and \texttt{make check-submit} against the final PDF at the \texttt{submit} phase whatever \texttt{\textbackslash lintphase} says, the check before you upload; run one rule with, for example, \texttt{make lint-essentials}. The same lint generates the draft PDF's \emph{Checks} page on every compile (\cref{app:latex:todo}), keeping the PDF and CI consistent.
